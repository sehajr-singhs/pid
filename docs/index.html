Piπd

CAD in, tuned robot out. Starting gains for FTC and FRC mechanisms, from physics, before the robot is built.

Open the demo (FAT MAN, FTC 19426)  ·  Code on GitHub

What it does

Reads a robot's CAD export and parts list, works out each mechanism's mass, inertia and gearing, and computes kS, kV, kA, kG and PIDF from motor datasheets. It checks them in a 1 kHz simulator, tunes them, and exports constants for Pedro Pathing, FTC Dashboard and WPILib. Then one logged test run on the real robot refits the gains with pid calibrate.

Why Pedro Pathing would partner

Pedro Pathing is the path follower a large share of FTC teams use. Its hardest part for a new team is tuning: the Foresight AutoTune procedures need a working, driving robot, and until then Constants.java is full of placeholders. Piπd fills that file from CAD before the robot exists, using Pedro's current API (ForesightConfig, MecanumConfig, PinpointConfig, checked against pedropathing.com):

  • FAT MAN starts at 100.66 in/s forward and 78.52 in/s strafe max velocity, plus natural deceleration from a friction model, instead of zeros.
  • Piπd also writes a tuning checklist that walks the team through Pedro's own AutoTune steps in order and says which constant each one replaces.
  • For Pedro, that means fewer teams stuck at setup, fewer "my robot spins in circles" support questions, and a path from Onshape straight into their library.

What a partnership could be: a "start from CAD" page in Pedro's docs that links to Piπd, and a check that Piπd's export stays in sync when Pedro's API changes. The last API change already broke the old docs pages, which Piπd caught.

Why MoSimulator would partner

MoSimulator is an FRC robot simulator with community robot mods (a Unity bundle, a C# .dll and a catalog). Building a mod is mostly hand work: modeling the hierarchy, picking joint limits and guessing PID values so the robot doesn't shake or fly apart. Piπd generates that from CAD:

  • hierarchy.json with joints, axes, limits and masses, params.json with per-joint gains from physics, and a C# skeleton that uses MoSim's real GenericJoint and PidConstants API.
  • For MoSim, that means more community robots that move like the real ones, faster, and an on-ramp from a team's actual CAD to a playable robot.

What a partnership could be: a Piπd export button listed in MoSim's modding docs, and MoSim's feedback on which joint types to support next.

Neither project has partnered with Piπd yet. These are the pitches, and both exports are in the repo to try.
